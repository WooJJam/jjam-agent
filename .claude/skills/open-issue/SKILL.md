# open-issue — 이슈 생성 + 브랜치 체크아웃

jjam-agent의 모든 작업은 이슈에서 시작한다. 이 스킬은 이슈 생성부터 작업 브랜치
체크아웃까지를 한 절차로 수행한다. `gh` CLI가 없으므로 GitHub API를 직접 호출한다
(동봉된 `create_issue.py` 사용).

## 절차

### 1. 타입 결정

| 타입 | 용도 |
|------|------|
| feat | 기능·스크립트·스킬 추가 |
| fix | 버그·오동작 수정 |
| docs | 스펙·계획·운영 문서 |
| infra | Terraform·EC2·스케줄러·배포 (과금 가능 작업) |
| chore | 설정·의존성·정리 |

요청 내용에서 타입이 명확하지 않으면 사용자에게 묻는다. 임의로 정하지 않는다.

### 2. 본문 구성 — 템플릿 필드 준수

`.github/ISSUE_TEMPLATE/<타입>.yml`의 필드 구조를 따르며, 본문은 GitHub 폼 렌더링과
동일한 형식(`### 필드라벨` + 내용)으로 작성한다. **필수 필드를 비워두지 않는다** —
대화 맥락으로 채울 수 없는 필수 필드는 사용자에게 묻는다.

- 공통: 도메인은 `finance | briefing | weather | cost-usage | hermes | workflow | 공통` 중 선택
- feat: 배경/목적 · 작업 항목(체크리스트) · 완료 기준 · 도메인. 작업 항목은 PR 단계에서
  대조되므로 구체적 단위로 쪼갠다
- fix: 현상 · 기대 동작 · 도메인 (재현 절차·원인 추정은 알면 포함)
- docs: 대상 문서 경로 · 변경 내용 · 도메인
- infra: 배경 · 대상 리소스 · 작업 항목 · **비용 영향 · 롤백 방법 · 완료 기준 전부 필수**
- chore: 작업 내용 · 이유

제목은 `[타입] 한 줄 요약` (템플릿의 title prefix와 동일). 본문·제목에 시크릿 값,
개인 금융 실데이터를 절대 넣지 않는다.

### 3. 생성 전 확인 게이트

- **infra 타입은 생성 전 반드시** 제목·라벨·비용 영향·롤백을 요약해 보여주고 사용자
  확인을 받는다 (과금 작업 안전장치).
- 그 외 타입은 필수 필드가 대화 맥락에서 명확하면 바로 생성하고, 내가 추측으로 채운
  필드가 있으면 생성 전에 요약을 보여주고 확인받는다.

### 4. 이슈 생성

본문을 임시 파일(스크래치패드)에 UTF-8로 저장한 뒤:

```bash
py .claude/skills/open-issue/create_issue.py \
  --title "[feat] 제목" \
  --body-file "본문파일경로" \
  --labels "feat,finance"
```

- 라벨은 `타입` + `도메인` (도메인이 "공통"이면 타입만)
- 출력의 이슈 번호·URL을 다음 단계에 사용한다

### 5. 브랜치 생성·체크아웃

```bash
git fetch origin
git switch -c <타입>/<이슈번호>-<슬러그> origin/main
```

- 슬러그: 영문 소문자-하이픈, 2~4단어 (예: `feat/12-finance-db-schema`)
- 반드시 **최신 origin/main 기준**으로 분기한다. 워킹 트리에 미커밋 변경이 있으면
  먼저 처리(커밋/스태시)를 사용자와 정한다

### 6. 보고

이슈 URL, 적용 라벨, 체크아웃된 브랜치명을 보고하고 곧바로 해당 작업에 착수한다.
이후 커밋 메시지에는 `(#이슈번호)`를 참조로 붙인다.

## 금지 사항

- 이슈 없이 작업 브랜치를 만들지 않는다 (이 스킬을 거치지 않는 예외는 사용자 지시뿐)
- PR 생성은 이 스킬의 범위가 아니다 — 작업 완료 후 별도 절차(/open-pr, 사용자 승인 필요)
- 토큰을 stdout·로그·이슈 본문에 출력하지 않는다
