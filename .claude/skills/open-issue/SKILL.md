# /open-issue — 이슈 생성 + 브랜치 체크아웃

jjam-agent의 모든 작업은 이슈에서 시작한다. 이 스킬은 `/open-issue` 명령어로
호출됐을 때만 실행한다. "이슈 만들어줘" 같은 자연어 요청에는 자동 발동하지 않고,
`/open-issue` 사용을 안내한다.

이슈 생성은 `gh` CLI를 사용한다. 시작 전에 `gh auth status`로 로그인 상태를
확인하고, 실패하면 사용자에게 `gh auth login`을 안내한 뒤 중단한다.

## 사전 체크 0 — 인자·의도 검증 (최우선)

명령어 인자(ARGUMENTS)를 다른 무엇보다 먼저 해석하고 검증한다:

- **인자 없음** → 대화 맥락에서 이슈로 만들 작업 내용을 수집한다 (없으면 사용자에게 질문)
- **인자로 이슈 내용·타입 제공** → 해석 결과("타입 X, 제목 Y로 이슈 생성")를 명시하고 진행
- **인자가 이 스킬의 목적(이슈 생성 + 브랜치 체크아웃)과 상반되거나**(예: "PR 작성",
  "머지해줘", "이슈 삭제"), **모호하거나, 해석이 두 가지 이상 가능하면** — 멋대로
  판단해서 진행하지 않는다. **반드시 사용자에게 질문해**(AskUserQuestion 또는 텍스트)
  의도를 확인한 뒤에만 진행한다. "아마 이런 뜻이겠지"로 절차를 시작하는 것 자체가
  금지다.

## 절차

### 1. 타입 결정

| 타입 | 용도 |
|------|------|
| feat | 기능·스크립트·스킬 추가 |
| fix | 버그·오동작 수정 |
| docs | 스펙·계획·운영 문서 |
| infra | Terraform·EC2·스케줄러·배포 (과금 가능 작업) |
| chore | 설정·의존성·정리 |

명령어 인자와 대화 맥락으로 타입이 명확하지 않으면 AskUserQuestion으로 선택받는다.
임의로 정하지 않는다.

### 2. 본문 작성 — 템플릿 필드 준수

`.github/ISSUE_TEMPLATE/<타입>.yml`의 필드 구조를 그대로 따라, GitHub 폼 렌더링과
동일한 형식(`### 필드라벨` 제목 + 내용)으로 작성한다.

- 한국어 서술, 기술 용어는 영어 유지. 모호한 수사 금지
- 필수 필드를 비우거나 플레이스홀더를 남기지 않는다 — 맥락으로 못 채우면 사용자에게 질문
- 제목·본문에 시크릿 값, 개인 금융 실데이터 절대 금지
- 도메인: `finance | briefing | weather | cost-usage | hermes | workflow | 공통`
- feat/infra의 "작업 항목" 체크리스트는 PR 단계에서 대조되므로 구체적 단위로 쪼갠다
- 제목: `[타입] 한 줄 요약` — 명사구, 마침표 없음, 커밋 prefix(`feat(scope):`) 금지

### 3. 생성 전 확인 게이트 (전 타입 필수)

이슈를 생성하기 전에 반드시 아래를 한 번에 보여주고 사용자 승인을 받는다:

- 제목
- 라벨 (타입 + 도메인)
- 본문 전문
- 생성할 브랜치명 제안: `<타입>/<번호>-<슬러그>` (번호는 생성 후 확정, 슬러그만 제시)

infra 타입은 비용 영향·롤백 방법을 요약에 별도 강조한다.
승인 없이 이슈를 생성하지 않는다. 수정 요청이 오면 반영 후 다시 확인받는다.

### 4. 이슈 생성

본문을 스크래치패드 임시파일(UTF-8)로 저장한 뒤:

```bash
gh issue create \
  --title "[feat] 제목" \
  --body-file "본문파일경로" \
  --label "feat" --label "finance"
```

- 라벨은 `--label 타입` + `--label 도메인` (도메인이 "공통"이면 타입만)
- **라벨은 아래 사전 정의 목록만 사용한다. 새 라벨 생성·목록 외 라벨(GitHub 기본
  라벨 bug/enhancement/documentation 등 포함) 사용 금지:**
  - 타입: `feat` `fix` `docs` `infra` `chore`
  - 도메인: `finance` `briefing` `weather` `cost-usage` `hermes` `workflow`
- 성공 시 이슈 URL이 출력된다 — URL 끝의 번호를 다음 단계에 사용

### 5. 브랜치 생성·체크아웃

```bash
git fetch origin
git switch -c <타입>/<이슈번호>-<슬러그> origin/main
```

- 슬러그: 영문 소문자-하이픈 2~4단어 (예: `feat/12-finance-db-schema`)
- 항상 최신 `origin/main` 기준으로 분기한다
- 워킹 트리에 미커밋 변경이 있으면 처리 방법(커밋/스태시)을 사용자와 정한 뒤 진행

### 6. 보고

이슈 URL·라벨·체크아웃된 브랜치명을 보고하고 해당 작업에 착수한다.
이후 이 브랜치의 커밋 메시지에는 `(#이슈번호)`를 참조로 붙인다.

## 금지 사항 (Anti-patterns)

- 인자·의도 검증(사전 체크 0) 생략 — 인자가 목적과 어긋나는데 질문 없이 진행
- 확인 게이트(3단계) 없이 이슈 생성
- 타입·라벨이 불명확한데 질문 없이 임의 배정
- 빈 템플릿 필드·플레이스홀더가 남은 본문
- 이슈 없이 작업 브랜치 생성 (예외는 사용자의 명시 지시뿐)
- PR 생성 — 이 스킬 범위 밖 (작업 완료 후 별도 /open-pr, 사용자 승인 필요)
- `gh api`·토큰 직접 취급 — 이슈 생성은 `gh issue create`만 사용한다
